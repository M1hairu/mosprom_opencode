# API площадки

Источник документа — таблица `site_documents`. Каждая строка содержит `site_id`,
монотонный `version`, `status`, JSONB `body`, роль автора и время. Записи неизменяемы.
Публикация и откат создают новую строку. Последняя опубликованная версия доступна
без входа. Новый черновик не заменяет публикацию.

## Контракт

`body` содержит `plan`, `zones`, `routes`, `facts`, `catalog`. Каждое поле сохраняет
исходный формат соответствующего файла `content/`. План хранится без потери
неизвестных полей и без нормализации исходного контура. Для проверки норм используется
типизированное представление `PlanDocument`. JSON Schema контента остаются только в
`content/schemas/`; их читает общий валидатор API и `scripts/check-content.py`.
Эти же схемы попадают в OpenAPI и в типы `make contracts`.

| Запрос | Доступ | Результат |
|---|---|---|
| `GET /api/sites/{site}/document` | публичный | последняя публикация; 404, если публикации нет |
| `GET /api/sites/{site}/draft` | editor | последний черновик |
| `PUT /api/sites/{site}/draft` | editor | тело — документ; новая версия черновика и находки |
| `POST /api/sites/{site}/publish` | editor | тело `{"version": N}`; новая публикация указанной версии |
| `POST /api/sites/{site}/rollback` | editor | тело `{"version": N}`; новая публикация старой версии после повторной проверки |
| `GET /api/sites/{site}/versions` | editor, manager, expert | метаданные всех версий, новые первыми |
| `GET /api/auth/me` | editor, manager, expert | подтверждённая роль |

Ответ с документом: `{site_id, version, status, author, created_at, body, findings}`.
Ошибка формы документа — 422 при сохранении. Ошибки содержания можно сохранить в
черновике. Публикация проверяет связи, G1–G3, G14 и нормы `/api/validate`. Любая находка
`error` даёт 422 с `detail.findings`; `warning` остаётся в успешном ответе.
Конкурирующая запись сериализуется блокировкой площадки. Конфликт первой записи
или номера версии даёт 409. Клиент может повторить запрос.

## Вход

HTTP Basic: логины `editor`, `manager`, `expert`. Пароли — `EDITOR_PASSWORD`,
`MANAGER_PASSWORD`, `EXPERT_PASSWORD` в `.env`. Пустое или отсутствующее значение
отключает вход этой роли. На публичной выкладке нужен HTTPS. Неверные данные дают 401
с `WWW-Authenticate`; известная роль без права на операцию — 403.

Редактор изменяет документы. Менеджер и эксперт читают список визитов и поток
`/api/sites/{site}/stream`. Запись только у менеджера: он меняет роль гостя и ведёт гостя
к зоне (`POST /api/visits/{visit_id}/events`, `src: manual`). Эксперт ещё читает публикацию
и метаданные версий; заявки (ПДн) ему закрыты (D-020).
Создание анонимного визита, события по токену гостя и экран зоны остаются публичными.
Пароль не входит в URL и не отправляется гостю.

## Импорт

```bash
make demo
make seed                            # явно content/plan-219.json → hall-219
make seed PLAN=plan-219-zoned.json    # другой выбранный план
```

API-образ включает канонические файлы `content/` и схемы. Первый корректный импорт
публикуется. Импорт с ошибками сохраняется черновиком и печатает находки. Повтор того же
содержимого не создаёт версию. Новое содержимое после первой публикации сохраняется
черновиком и не заменяет правки редактора. Сравнение идёт со всей историей импортов.

`catalog.json` общий для всех `plan*.json`. Импорт берёт стены, зоны и объекты выбранного
плана и добавляет в его `catalog.objectTypes` типы других планов `content/`. Так ссылки
`plan_type` проверяются по одному плану документа. Нормы проверяются по выбранному плану
без изменений. Зонированные планы сейчас дают `PASSAGE_TOO_NARROW` (#110): их импорт
остаётся черновиком. Пока опубликованной версии нет, корректный импорт публикуется, даже
если раньше был черновик. Пока корректная версия не опубликована, публичный GET вернёт 404.

Для локальной проверки: `make check`. Контрактные тесты используют SQLite, отдельные
тесты миграций формируют SQL PostgreSQL. Работа compose требует Docker.
